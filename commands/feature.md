Spawn `idleflow:planner` with: the issue path (`.idleflow/runs/active/issue.md`), context.md path, the `$LESSONS` path, conventions path, plan template path, output path `.idleflow/runs/active/plan.md`, the size, `greenfield`, the implementer cap for this size, the diff limit for this run, `STEP_MUTATION` from `conf`, the time log path (`bash "$RUN" path time-log`), the `design.md` and `DESIGN_SYSTEM` paths when step 2c ran, whether R3 and R4 ran (when they did not, a plan that adds a dependency anyway lists it under "Open questions" for the human), and when `docs: yes` the paths of `prd.md` (with `template` when it is missing or its first line is still the template's `# <Project name> — product requirements`, else `written`; checked at this first call, whatever `greenfield` says, and the same value goes to every later planner call in the run), `progress.md`, `index.md` plus `templates/prd.md`. Every later planner call (a revision, a one-task revision) gets the issue path too, and comes right after `bash "$RUN" keep plan.md`, which keeps the plan it replaces as `plan.<n>.md`, so any revision can be undone exactly. Wait.

Read `plan.md` once now; keep the task list, groups, owned globs, models and merge order in working memory and do not re-read the plan unless it is revised.

If "Open questions for the human" is non-empty, ask them now with AskUserQuestion and append one line per answer to `.idleflow/runs/active/decisions.md`: `Q<n>: <answer>` (an answer the human changes later in the run is appended the same way; the newest line for an id is the decision). If the human is not present, write `Q<n>: default (human not present)` for each and say so. When any answer differs from the planner's stated default, spawn `idleflow:planner` in revision mode with the issue and decisions paths: it carries each answer into every section that depends on it (the Goal, each task's acceptance, notes and levers, "Verification after merge"), so the section an implementer gets matches the decision. Then re-read plan.md. You never edit plan.md yourself.

**Plan check**, after this and every later planner call that writes plan.md (a revision, a split): `bash "$RUN" plan-check`. It matches with the guard's own matcher, so a plan it passes is one the guard lets build: each file a task's entry points or acceptance name must be in its `owns:` or `shared_files`, and no `owns:` glob may cover a protected file (the list in the planner's ownership rule: `prd.md`, `progress.md`, `index.md`, `CLAUDE.md`, the lessons file, anything under `.idleflow/`, and the Claude Code configuration `.claude/settings.json`, `.claude/settings.local.json`, `.claude/agents/` and `.claude/hooks/`), directly or through a wide glob (`.claude/**`). ## 4. Debate (Opus × 2) — only for size L or risk high (or `STEP_DEBATE` says otherwise)

Otherwise skip to the "Plan locked" line at the end of this step.

Round 1, both in parallel: `idleflow:red-team` → `debate/round-1-red.md` and `idleflow:cost-critic` → `debate/round-1-cost.md`, each with the issue, plan.md and context.md paths.

Round 2, in turn, so each answer has something to answer: first `idleflow:red-team` → `debate/round-2-red.md`, with the round-1 inputs and `round-1-cost.md`; once that file exists (`test -s`; a red team that replied without writing it is re-spawned once, and a second miss stops the run), `idleflow:cost-critic` → `debate/round-2-cost.md`, with the round-1 inputs, `round-1-red.md` and `round-2-red.md`. Rounds are capped at `DEBATE_ROUNDS`; never run a third.

Before the revision, the human decides what gets cut. Read the debate files (four, or two when `DEBATE_ROUNDS` is 1) and list every cost cut (`C<n>`) still standing after the last round (not withdrawn) and every red-team finding whose fix the cost critic contested, one line each: what it changes, what it saves (from `saves:`), what it risks (from `risk:` or the red team's `claim:`), with its id last in parentheses. Ask with AskUserQuestion, `multiSelect: true`, one option per item (label = the change in plain words with the id in parentheses; description = saves and risks), at most four options per question and four questions per call; use more calls when there are more items. Selected means accepted. Append the answers to `decisions.md`, one line per item: `<id>: accepted` or `<id>: rejected`. If the human is not present, skip the question and write no line for these items; the planner adjudicates them as before. Red-team findings nobody contested are not asked about.

Then spawn `idleflow:planner` in revision mode with the issue path, the debate paths and the `decisions.md` path; it rewrites plan.md with a "Debate resolution" section. Re-read plan.md. If any resolution is `deferred to human`, ask now, append `<id>: <answer>` to `decisions.md`, and spawn the planner in revision mode once more with only the issue and decisions paths; re-read plan.md.

When `git status --porcelain -- prd.md` (and `DESIGN_SYSTEM` when step 2c ran) shows a change (the planner filled the template or applied a yes, the designer revised the design system), run `bash "$RUN" snapshot` first, before any worktree exists, so the product the plan was written against is committed with it; the gate keeps the base it ran on (`gate_base`). Then tell the human: `Plan locked: <N> tasks in <G> groups, est <L> lines. Building.` If there is more than one group, one line per group.

## 5. Build (parallel worktrees)

Before the group's worktrees: the services check (step 0, "The services the tests need"). Steps 5 to 8 run once per group, in plan order: a group's tasks are built, gated, reviewed and merged before the next group's worktrees exist. A later group builds on the earlier groups' code: `wt add` branches from the run's branch as it is when the task starts, so it holds every merge so far, and records that commit as the task's base. Within a group, all tasks run in parallel, at most the implementer cap (a larger group is a planner error: split it into waves):

0. **Blocked tasks first.** For every task in the group whose `blocked_until:` (`bash "$RUN" plan-field <task-id> blocked_until`) is neither empty nor `none`, find the evidence it waits for in what the earlier groups left: their reports, review files, and the CI or verification output that names it. When it is not there yet (a CI job not run), ask the human for it with AskUserQuestion; with no human present, stop with `needs-human` and say what the task waits for. Then spawn `idleflow:planner` for a one-task revision with the issue path, the task id, the field's text and that evidence; it writes the task's final section with `blocked_until: none`. Re-read that section. `wt add` exits 8 for a task still blocked: never edit the field yourself.
1. For every task in the group:
   ```
   WT=$(bash "$RUN" wt add <task-id>)
   bash "$RUN" own <task-id> '<json array of the task's owned globs from plan.md>'
   bash "$RUN" set tasks.<task-id>.status '"building"'
   ```
   `wt add` exits 8 when the task is still `blocked_until` a revision: run step 0's revision for it once more, and if it exits 8 again, remove the group's worktrees, run the **Plugin gaps** question from step 9 and `bash "$RUN" finish needs-human` with the field's text. It exits 7 when `worktree_setup` is not approved (step 0 asks first, so this means the command changed mid-run: ask again, then re-run `wt add`). It exits 6 when the repo's `worktree_setup` (conventions "Repo fit") fails or changes a tracked file: show its message and the setup log path, remove the group's worktrees, run the **Plugin gaps** question from step 9, and `bash "$RUN" finish needs-human`; the human fixes the command first. `wt add` records the task's own base sha in `run.json` (`bash "$RUN" get tasks.<task-id>.base_sha`); that sha, not the run's, is what the gate, the auditor and the reviewers diff against.
2. Spawn one implementer per task in a single message so they run concurrently: `idleflow:implementer` for `model: sonnet`, `idleflow:implementer-hard` for `model: opus`. Prompt each with only: its task id, its worktree path, the task's plan extract (paste the output of `bash "$RUN" extract <task-id>`: the plan's "Stack & style constraints" and "Interfaces" sections, which every task is written against, then the task's own section; it is the one exception to the no-paste rule, because the implementer must not read other tasks), the absolute paths of `context.md` and `.idleflow/conventions.md`, `co_author_claude: <value>` (from `CLAUDE.md`; `no` when the file or the line is absent), `Run commands with: bash "<absolute path of run.sh>" exec <task-id> -- <command>` (the task's own port and temp folder), `Repo gate: <command>` when the run has a gate, and `Known base failures: <absolute path>` when `.idleflow/runs/active/known-failures.md` exists. For a `ui: true` task, also the `design.md`, `DESIGN_SYSTEM` and `${CLAUDE_PLUGIN_ROOT}/procedures/design.md` paths. Nothing else; the report format is in the agent's own definition.
3. Wait for all of them. When the harness reports an agent's token use, record it (`bash "$RUN" set tasks.<task-id>.tokens <n>`, added up across retries); never estimate one. For each, `bash "$RUN" report <task-id>` copies its report to `.idleflow/runs/active/tasks/<task-id>/report.md`; read `status`, `deviations`, `blocked_on` and `base_failures` from there. Append each `base_failures:` line not already listed to `.idleflow/runs/active/known-failures.md`, as `- <test or check> — <fails | flaky k of n> — "<the failure line>" — <task-id> base job <n>`: the base is the run's, so every later implementer and reviewer gets it, with or without a gate. Run `report` again after every later implementer run for the task (a retry, a conflict re-run) before reading it; `gate` also refreshes the copy when the worktree's is newer. Never edit a stored report yourself: a wrong report goes back to the implementer.

   **Retries are per task.** A task may be retried while `bash "$RUN" get tasks.<task-id>.retries` is below `MAX_RETRIES` (unset counts as 0). Each retry runs `bash "$RUN" inc tasks.<task-id>.retries` and `bash "$RUN" inc retries` (the run total, kept for the log). A task out of retries stops the run as in step 7.
   - `blocked` with `blocked_on: environment: …` → not a retry: ask with AskUserQuestion, showing the cause and its evidence: **Fixed, run it again** (the human fixed the cause; re-spawn the task's implementer with the same prompt; no retry is counted) / **Stop the run** (remove the worktrees, run the **Plugin gaps** question from step 9, `bash "$RUN" finish needs-human`, and name the cause).
   - `blocked` on a file → if the needed file belongs to another task in this group, finish and merge the group, then re-run the blocked task in group N+1, in a new worktree (`wt rm <task-id>`, then `wt add <task-id>`, so it starts from the merged group), with the extra glob added by `bash "$RUN" own` **and** in the task's `owns:` list in plan.md (reviewers read `ownership.json`; the plan is for humans). If the file belongs to no task, add it the same way and re-spawn once. Neither is a retry: the plan's map was short, and no work was rejected (`bash "$RUN" inc tasks.<task-id>.extensions`); a task blocked on a file a second time takes the retry path.
   - `partial` whose `deviations` are `none` or name only A-ids listed under `after_merge:`, each written `verify: browser after merge` in the task's extract (`bash "$RUN" extract <task-id>`) → `done`: no retry is spent on a check that cannot run before the merge, which the design check after the last merge covers. An A-id listed there whose `verify:` is anything else is a deviation like any other.
   - `partial` with any other deviation → a plan defect, and a retry: send the deviation and the issue path to the planner for a one-task revision, then re-spawn on `idleflow:implementer-hard` as every retry is.
   - `done` → continue.

## 6. Gate each task

For each done task: `bash "$RUN" gate <task-id> [limit]` → JSON (pass the greenfield limit when it applies). It counts the task's commits only (`<base>..HEAD`, what would merge); `uncommitted` and `uncommitted_paths` name what the worktree holds outside them, which never merges.

- `ok` → review.
- `audit` or `split` → `bash "$RUN" inc gate_trips`; spawn `idleflow:diff-auditor` with the task's plan extract, the gate JSON, the worktree path and the task's base sha. Then:
  - `accept` → review.
  - `reject` → `bash "$RUN" set tasks.<id>.status '"building"'`, send the auditor's reason to the implementer as a retry (step 5's retry rule), re-gate.
  - `split` → `bash "$RUN" set tasks.<id>.status '"split"'`, `bash "$RUN" wt rm <task-id>`; send the auditor's sub-tasks and globs and the issue path to `idleflow:planner` for a one-task revision that replaces the task with a new group, numbered after the plan's highest task id; re-read the plan; register ownership. The new group runs steps 5 to 8 after the rest of the current group is merged and before the next group of the plan. You never edit the task list yourself.

**Retroactive upgrade:** if size was S and any gate `total` exceeds `SIZE_S_OVERRUN`, set size to M so step 7 runs the conformance reviewer as well. The debate does not run after the fact; it follows `risk`, which a bigger diff does not change.

## 7. Review (Opus + Sonnet, per task, in parallel)

Before the group's reviewers: the services check (step 0, "The services the tests need"). Size S: `idleflow:review-correct` only. M and L: `idleflow:review-correct` and `idleflow:review-conform` for every task of the group in one message. A `ui: true` task at any size also gets the design reviewer, with the worktree path, base sha, the task's plan extract, the `design.md`, `DESIGN_SYSTEM` and `procedures/design.md` paths, the output path `review/<id>-design.md`, and, when `bash "$RUN" get preview` is not empty and approved (`bash "$RUN" commands`), the two commands `bash "<absolute path of run.sh>" preview <id> start` and `... preview <id> stop` (the reviewer runs the app only through them); under `preview_in: main` in conventions with an approved preview, the app runs only from the main checkout, so it gets `Screenshots: after the merge` instead of those commands (without an approved preview it gets neither, as before). Each gets: the worktree path, the task's base sha, the task's plan extract (paste), the report path under `tasks/<id>/`, the output path under `review/`, the `ownership.json` path (the authority on owned globs), and `bash "<absolute path of run.sh>" unowned <id>`, the ownership check both reviewers run; `review-correct` also gets `Run commands with: bash "<absolute path of run.sh>" exec <id> -- <command>`. When the run has a gate, `review-correct` also gets the gate command; when `known-failures.md` exists, it also gets that path, gate or no gate. The conformance reviewer also gets the `context.md`, `.idleflow/conventions.md` and `$LESSONS` paths and the value of `co_author_claude` from `CLAUDE.md` (`no` if there is no such file). Both run in parallel; the correctness reviewer runs tests with caches disabled and the conformance reviewer ignores cache directories, so they do not pollute each other.

A reply counts only once its review file exists (`test -s <output path>`): the retro and any retry read the file, never the reply. A reviewer that replied without writing it is re-spawned once with the same prompt; a second miss stops the run as below. Before re-running a reviewer on the same task (after a retry or a fix round), move its previous file aside with `bash "$RUN" keep --move review/<id>-<kind>.md` (it becomes `review/<id>-<kind>.<n>.md`, n = 1, 2, …), so the check sees only the new file and the retro keeps the old one.

For each task:
- **Unverified checks.** Read them from the review file's `unverified:` line, never from the reply. They are checks no one could decide, for a cause outside the task: never a retry and never a pass. A `base` entry is a criterion whose own check fails on the base the same way, a fault of the plan: append it to `.idleflow/runs/active/known-failures.md` as `- <the failing check> (<A-id>) — fails — "<the failure line>" — <task-id> base job <n>` unless a line already names that task and A-id (every task numbers its criteria from A1), so the reports keep it whatever is answered, then ask with AskUserQuestion, showing the criterion, the failing set and the two job numbers: **Merge without it** (the entry is closed; the criterion stays unverified and is reported) / **Revise the criterion** (send the entry and the issue path to the planner for a one-task revision of that criterion, as step 5 does; then move that review file aside as below and re-run that reviewer; no retry is counted) / **Stop the run** (stop as below, with `needs-human`). A `ci <job name>` entry for a criterion the plan does not write as `verify: ci <job name>` is the reviewer's error: move that review file aside as above and re-run that reviewer once with the plan's `verify:` line quoted, counting no retry; the same entry again is a reject. An `environment` entry holds the task before merge: ask with AskUserQuestion, showing each entry and its evidence: **Fixed, review again** (the human fixed the cause; move that review file aside as above and re-run that reviewer; no retry is counted) / **Merge without it** (the entry is closed and stays in the review file for the run's reports) / **Stop the run** (stop as below, with `needs-human`). `ci <job name>` and `tool: …` entries ask nothing; they are reported as below. A review that also rejects takes its remedy below as usual, and its entries are judged again in the next review.
- **Reporting them.** Every message that ends the run, the final message and each stop with `needs-human` alike, lists the findings the current reviews of the tasks already merged still hold, and those of the browser check after merge, each once with its fix command from step 8 "Findings after merge" (`bash "$RUN" findings <their ids> merged`: one line each, with its severity or kind and review file; an approving review keeps its minor findings, and a `major` below the reject threshold, so the human can fix them or file a follow-up before the work ships), then the `unverified:` entries of those tasks and of `review/merged-correct.md` and `review/merged-design.md`, from their current review files under `.idleflow/runs/active/review/` (not the moved-aside `.<n>.md` ones), read before `finish`, in four groups: CI jobs that must pass before the work ships, each with the criteria it proves (a red job is a failed verification, and a new run fixes it); checks merged without because the environment could not run them; criteria whose own check fails on the base too, from the lines of `known-failures.md` that name an A-id of a task that merged, each with `/idleflow:fix "<the failing check> fails on <base branch> (found in run <id>)"`; checks no tool could make.
- every reviewer that ran approves and no `environment` or `base` entry is still open → `bash "$RUN" set tasks.<id>.status '"approved"'`.
- every reply → `bash "$RUN" inc review_findings <n>` with the n in its `(<n> findings…)`, whatever the verdict (a `, <k> unverified` suffix is not counted).
- any reject → **the remedy follows the findings.** Read the `remedy:` line of each rejecting review file, never the reply (a missing or unknown value is `rebuild`; a `reword <sha>` reply, from a project's replacement of the conformance reviewer written before remedies, is `message`); the heaviest of them decides, in the order `message` < `report` < `edit` < `rebuild`. It takes the `rebuild` path below when it is `rebuild`, when `bash "$RUN" get tasks.<id>.fixes` has reached 2 (unset counts as 0), or when the last fix round's report names a finding under `unfixed:` (its `deviations:` keep what the build reported and decide nothing here). Otherwise it takes a lighter round, which is not a retry (`bash "$RUN" inc tasks.<id>.fixes` and `bash "$RUN" inc fixes`):
  - **Commit messages first**, whatever the remedy: for each finding in the rejecting review files whose `fix:` reads `reword commit <sha> to: "<message>"`, write the message exactly as quoted, with no line added, to `.idleflow/runs/active/tasks/<id>/message-<n>.txt` (n = 1, 2, …), then reword them all in one call: `bash "$RUN" reword <id> <sha> <path> [<sha> <path>...]`. It re-creates the task's commits from the oldest flagged one on, on the same trees, so no file changes; you never touch the worktree's files. If it fails, show its message and take the `rebuild` path.
  - **Then the remedy:** `message` needs nothing more. `report`: re-spawn the task's implementer (the model the plan gives the task) with its original prompt plus `Fix mode: report` and the rejecting review file paths, then `bash "$RUN" report <id>`. `edit`: the same with `Fix mode: edit`, then `bash "$RUN" report <id>` and re-gate (step 6).
  - **Then review again:** move aside and re-run the reviewers that rejected; after an `edit`, which changes code, every reviewer of the task.
  - `rebuild`, the retry path: if the task has a retry left (step 5's retry rule), count it, `bash "$RUN" set tasks.<id>.status '"building"'`, re-spawn the task's implementer (`idleflow:implementer-hard` for the retry regardless of original model; quality first) with its original prompt plus the paths of the rejecting review files, then `bash "$RUN" report <id>`, re-gate and re-review that task only. Else stop: tell the human which task, which findings (titles only) and the review file paths; remove worktrees (`bash "$RUN" wt list` → `wt rm` each), run the **Plugin gaps** question from step 9, then `bash "$RUN" finish needs-human`. Merge nothing more: earlier groups' merges stay on the branch, and the message names the groups already merged and their tasks.

## 8. Merge and verify

In plan merge order, the group's tasks: `bash "$RUN" merge <task-id>`. It reads the task's title from its `### <task-id>: <title>` heading in plan.md; under `conventional` and `plain` the title follows `chore: merge ` or `Merge ` in the merge subject. It merges the task's branch as committed and approved; a `merge <id>: uncommitted in the worktree, not merged` line names what it left behind; repeat it to the human. Exit 3 (`CONFLICT`) means the ownership map was wrong; do not resolve by hand. Re-run the later task against the new base (`wt rm`, `wt add <id> HEAD`, `set tasks.<id>.status '"building"'`, re-spawn with the same prompt), re-gate, re-review, merge. One attempt; then stop and ask the human as in step 7. Exit 4 is a different failure (unapproved task, unknown branch, dirty checkout): show the message, remove the worktrees, run the **Plugin gaps** question from step 9, and `bash "$RUN" finish needs-human`.

Then the next group starts at step 5. After the last group's merges, run the services check (step 0), then `bash "$RUN" repo-gate main` when the run has a gate, then the plan's "Verification after merge" command; a gate failure the base did not have counts as a failed verification, unless its output shows an `environment` cause as `review-correct` defines it: then ask as in step 7 (**Fixed, run it again**, which re-runs the gate / **Finish without it**, which appends `- repo gate on main — environment: <the cause> — <the quoted output line>` under an `unverified:` line in `review/merged-correct.md`, creating the file with that line when it is missing, so the reports read it like any review's entry / **Stop the run**). **Browser check after merge**, when it passes and conventions say `preview_in: main` (the app runs only from the main checkout) and any task is `ui: true` or has a `verify: browser after merge` criterion. With an approved preview (`bash "$RUN" commands`), spawn `idleflow:review-design` in merged mode with the repo root, the range `<bash "$RUN" get base_sha>..HEAD`, the plan extract of every such task, the `design.md`, `DESIGN_SYSTEM` and `procedures/design.md` paths when step 2c ran, the output path `review/merged-design.md` and the commands `bash "<absolute path of run.sh>" preview main start` and `... preview main stop`. A `reject` there is a failed verification. Its `unverified:` entries are routed as in step 7: an `environment` entry asks **Fixed, review again** / **Finish without it** / **Stop the run**, and every entry is reported with the merged tasks' (step 7, "Reporting them"), as are its findings (`bash "$RUN" findings merged`). Without an approved preview, nothing runs: write `review/merged-design.md` with an `unverified:` line and, under it, `- <A-id> — tool: no approved preview` for each of those tasks' `verify: browser after merge` criteria, so they are reported as checks no tool could make.

Only when the gate, the verification command and the browser check all pass, `bash "$RUN" docs` regenerates the generated blocks in the repo's Markdown from the merged code; when it prints `regenerated <files>`, commit exactly those files: `docs: regenerate generated sections`. A first run creates the repo's scripts, so `CLAUDE.md` "Commands" (a generated block) is filled here. On a failed verification (the gate, the verification command or a browser-check `reject`) or a failing `docs`, show the human the head of the failing output or the findings, remove the worktrees, run the **Plugin gaps** question from step 9, and finish with `needs-human`; the gate proposal below is skipped. A stop before the browser check also lists, as not checked, the `verify: browser after merge` criteria and the screenshot items it would have covered. Never spawn agents to fix a red suite; that is a new run, which **Findings after merge** hands on.

**Findings after merge.** A run ends at its merge: nothing raised once a group has merged, on files a merged task changed, is fixed in this run, and you never edit code yourself. Such a finding is a gate on main that fails beyond the base's failures for a cause other than `environment` (that one is an `unverified:` entry, above), a failing "Verification after merge" command, a `reject` or a finding of the browser check after merge, and anything the host or the human raises once merges began (a security review, a hook's report, a comment). Record each as it is raised, as one entry in `.idleflow/runs/active/after-merge.md`: a line `- <file, or the check> — <the finding in one sentence> — <where it came from>` and under it its follow-up, `  /idleflow:fix "<the finding> in <file, or the check> (found after run <id>)"`, with any double quote in the finding written as a single one. Every message that ends the run, the final message and a `needs-human` stop alike, lists those entries with their commands after the findings and `unverified:` entries of step 7 "Reporting them" (a browser-check finding appears once, here, with its command), and tells the human not to push until they have run: each is a small run with its own review. A `needs-human` stop that lists any ends, like the final message, with the **End the session** / **Keep working** question of step 9, so the handoff keeps them.

**Gate proposal**, after a passing verification: when `gate:` in conventions is `unset` and `bash "$RUN" detect` prints a `suggest gate:` line, ask with AskUserQuestion: **Make it the gate (Recommended)**, showing the exact command / **Not now** (append `- declined: gate -> <command> (run <ID>)` to `.idleflow/suggestions.md`). On a yes, write the `gate:` line in conventions, commit only that file (`chore: set the repo gate`), then `bash "$RUN" approve gate`: the answer approves that exact text. The next run gates on it.

## 9. Retro and finish

`NOTE=$(bash "$RUN" session-name)` when `docs: yes`. First decide the release tag: if `CLAUDE.md` says `releases: github-tagged` and this run completes a milestone (every box under it in `progress.md` "Milestones" is ticked, or is one this run's merged tasks make true), propose `vX.Y.Z` by the rule in `CLAUDE.md` "Releases". Spawn `idleflow:retro` with the run directory path, the time log path, the plugin's `templates/time-log.md` path, the `$NOTE` path, the `$LESSONS` path, the progress and index paths and the sessions folder (`bash "$RUN" path progress|index|sessions`) and `index_rewrite` from conventions, the output of `bash "$RUN" conf`, the `docs:` value and that tag when there is one. When `docs: yes` it also writes the session note and updates `progress.md` and `index.md`, and commits them. **Plugin gaps**, before every `finish` in this run (`done`, `needs-human`, or any other status), after the retro has run when it runs: read `.idleflow/runs/active/gaps.md` if it exists, plus any gap you hit yourself. If there are lines, list them and ask once with AskUserQuestion: **Report them to Idle-Sync/idleflow** / **Not now**. On yes, read `${CLAUDE_PLUGIN_ROOT}/commands/plugin-feedback.md` and follow its batch mode with the lines and the run id; it opens the issues from the human's GitHub account and asks nothing further. Never open an issue without that answer.

Then remove worktrees: `bash "$RUN" wt list` → `bash "$RUN" wt rm <id>` each. Collect the `unverified:` entries (step 7, "Reporting them") and the entries of `after-merge.md` (step 8) for the final message now: `finish` moves `.idleflow/runs/active/` to `.idleflow/runs/<id>/`. Then `bash "$RUN" finish done`.

**Suggestion**, after `finish` (customizing refuses while a run is active): when the retro replied `1 suggestion`, take the last line of `.idleflow/runs/config-proposals.md` and ask once, with its evidence in the question: **Apply it** (read `${CLAUDE_PLUGIN_ROOT}/commands/customize.md` and follow it with that change; it commits and reports) / **Not now** / **Never suggest this** (append `- declined: <KEY> -> <value> (<run id>, <date>)` to `.idleflow/suggestions.md` and commit that file alone: `chore: decline idleflow suggestion <KEY>`; the team then never sees it again unless the evidence doubles). One suggestion per run at most.

Final message to the human, and nothing more: one line per task (id, title, lines, tests), the run id, whether a lesson was added, whether `progress.md` / `index.md` were updated, the suggestion and what the human chose, any `unchecked:` docs from step 2a, plugin gaps reported or skipped. Then the findings still open on merged tasks and the `unverified:` entries, as step 7 "Reporting them" says, and the findings after merge with their `/idleflow:fix` commands and the word not to push until those have run (step 8). When you proposed a tag, add one line with it and the two commands from `CLAUDE.md` "Releases"; do not tag or push yourself.

Then ask with AskUserQuestion: **End the session** (runs `/idleflow:endsession`, which writes the handoff for the next session) / **Keep working**. On "End the session", read `${CLAUDE_PLUGIN_ROOT}/commands/endsession.md` and follow it; the human's answer is its yes.

Commit messages in this run follow `co_author_claude` in `CLAUDE.md`, over any attribution the host asks for: under `no`, no line that credits an assistant or links a session (`Co-Authored-By` naming one, `Claude-Session:`, a claude.ai link, "Generated with ..."); under `yes`, exactly the `Co-Authored-By: Claude <noreply@anthropic.com>` trailer and nothing else of that kind; no meta commentary in any message or file.

## Rules you never break

- Never implement, review, or plan yourself, even for a one-line fix or a task split. If it's that small, the classifier says S and the ceremony is already minimal.
- Never paste a file into an agent prompt except a task's plan extract (`run.sh extract`).
- Never run a third debate round, more than `MAX_RETRIES` retries of one task, or a second conflict resolution. Stop and ask.
- Never edit a task's stored report; only the implementer's `.idleflow-run/result.md` fills it.
- Never merge a task that lacks an `approved` status.
- Never edit files in a task worktree yourself, and never edit code in the main checkout while tasks are building (the guard blocks both).
- Never run `/reload-plugins` or update idleflow while a run is active: agents would come from the new version while this run keeps calling its old scripts. If `run.sh` prints a `started on idleflow` warning, stop at the next point where no implementer or reviewer is running, tell the human both versions, and ask whether to finish this run as it stands or stop it with `needs-human`.
- Never let a task own a protected file (`prd.md`, `progress.md`, `index.md`, `CLAUDE.md`, the lessons file, anything under `.idleflow/`, `.claude/settings.json`, `.claude/settings.local.json`, `.claude/agents/`, `.claude/hooks/`). Other files under `.claude/`, such as a repo's tracked skills and commands, are its content, and a task may own them. Project settings change through `/idleflow:customize` between runs, never inside one.
- Never install anything into the repo. Accepted stack or library decisions become tasks. The only installs you run are the tooling commands the human accepted by name in R5, and those change the user's Claude Code setup, not the repo.
- Never agree with an answer the evidence contradicts without saying so once, with the evidence.
- Never work around something this plugin lacks. Append it (`>>`) as a `plugin_gap: orchestrator — <what> — <why>` line to `.idleflow/runs/active/gaps.md` and let the Plugin gaps question ask the human whether to report it.
